# 额度层详细设计（自研用量配额，对齐官方商业版口径）

> 背景：官方商业版（KnowFlow 企业版）在 v0.1.1 带了用量配额，公众号文章《DeepSeek Harness 桌面端、昇腾 ARM 适配、用量配额、问数知识库专家嵌入网页》明确了功能口径；文末也明说「用量配额属于商业版」。开源侧 v0.1.1 开放了实现它需要的全部接口：判定（`conversations/quota.py` 的 `quota.set`）、用量页标签页（`admin.usage.tabs`）、我的用量顶栏（`settings.usage.top`）、输入框拦截提醒（`chat.composer.top` 的 `block(reason)`）。本设计在 acme 扩展里自研同等功能，不动 KnowWork 的任何文件。

## 1. 官方口径（照文章逐条对齐）

- 系统管理员在「系统 → 空间管理」给每个空间定**每月 token 总额**，不定 = 不限。
- 空间管理员在「管理 → 用量 → 额度」往下分：**空间默认**（每人）、**部门/用户组默认**、**个人额度**；一个人同时在多个部门/用户组里，**取其中最高的那个**；个人设置覆盖组默认。
- **临时加额**：某人本月要多用，加一笔，**月底自动失效**。
- 可设成**超了只提醒、不拦截**。
- **每次改动都有记录**（变更记录）。
- 额度页：顶部四卡（空间本月总额 / 个人默认额度 / 已分配合计 / 下次恢复=每月 1 日），中部「最近 30 天每人用了多少」参考（平均/中位数/P90，建议值 = P90 向上取整成好记的数，折算约多少轮对话、填了单价的折算多少元，一键「填入默认额度」），下部按成员列表（本月已用/本月额度/额度来自/状态——85% 标「接近上限」/操作：加额、设额度）。
- **统一生效**：网页、桌面端、IM 机器人、网页嵌入、定时任务，开始一轮之前判一次；进行中的轮不打断。
- 员工侧：「设置 → 我的用量」看本月剩余、哪天恢复；快用完时**输入框上方提醒**（官方示例文案「本月额度已用 85%，还剩 75.2 万 token」）；用完了说清楚为什么发不出去、哪天恢复。
- **公开嵌入和 IM 未认出身份的访客只算空间总额**。
- 系统自己调模型的部分（起标题、对话摘要、知识库解析）不算进额度（官方这一版如此）。

## 2. 用量口径（「本月已用」怎么算）

- 数据源：内核 `usage` 记录（`models/usage.py`，宿主事件流落库，含 `workspace_id / user_id / input_tokens / output_tokens / total_tokens / occurred_at`）——与统计页「按成员」**同一份来源、同一条聚合**，管理员在两个页面看到的数一致，可解释。
- 聚合：`SUM(total_tokens) WHERE user_id = ? AND occurred_at ∈ [本月 1 日 0 点, 下月 1 日)`，时区用部署时区（`TZ`，默认 Asia/Shanghai）——与统计页「本月」口径一致。
- 系统自调模型（起标题、摘要、导读）在 usage 里也记在对话所属人名下，与官方「不算进额度」存在差异。第一版**不区分**（统计页本来就按人全量计）；若要排除，后续在聚合处按 `conversation_id`/来源过滤即可，是口径参数不是结构问题。
- 折算轮数：取最近 30 天 `轮数 = SUM(total_tokens) / COUNT(DISTINCT (conversation_id, turn))` 的平均值；费用折算用模型单价（内核统计已有的口径）。

## 3. 判定链路（`quota.set`）

```
TurnStart(workspace_id, user_id, conversation_id, trigger)
  → 解析这个人本月的额度（见 §4）
  → 聚合本月已用（usage）
  → 已用 + 预估 ≥ 额度？
      是 → 拦截模式：抛 QuotaExceeded(message, scope, resets_on=下月 1 日)
           仅提醒模式：放行（前端经 settings.usage.top / chat.composer.top 提醒）
      否 → 返回
```

- 登记：`Enterprise.setup_api` 里 `ctx.quota.set(check)`（合同只允许一份判定）。
- **成员判定**：`user.kind == 'person'` 才算个人/组额度；`channel`、`external`（网页嵌入自动建的外部用户、IM 未认出的渠道账号）**只判空间总额**（对齐官方）。
- **空间总额**：对所有人（含成员）独立判一层——个人额度过了、空间总额满了照样拦（scope='workspace'）。
- **临时加额**：叠加在该人本月额度上（`个人有效额度 = 生效额度 + 本月临时加额合计`），自然月月底失效（行上带月份，查询时只取当月）。
- **只提醒不拦截**：mode 记在每条规则上（空间总额、个人默认、组默认、个人额度各自可配，第一版先做空间总额与个人默认两级）。仅提醒时判定放行，超额状态由前端经 `settings.usage.top` 与 `chat.composer.top` 提醒。
- **性能**：每轮开始多 2～3 条索引查询（规则 + 聚合）。聚合带 `occurred_at` 范围条件走 usage 表的时间索引；第一版不加缓存（一轮一次，量级可控），后续有压力再加进程内 30s 缓存。
- **不打断进行中的轮**：判定只在开始一轮时调（内核约定），无需额外处理。
- **月切换**：按查询时刻的自然月聚合，无状态、无定时任务；「下次恢复 = 下月 1 日」直接由日期推。

## 4. 额度解析规则（优先级）

```
个人有效额度 = (个人额度 ?? max(部门默认, 用户组默认) ?? 空间默认 ?? 不限) + 本月临时加额合计
多部门/组取最高：MAX(组默认)后再被个人覆盖
「不限」：没有任何一层配置 → 该层不判
空间总额独立一层：空间设了才判
```

失败关闭口径与内核一致：判定内部出错（查库失败等）**放行并记日志**——额度是运营手段，不能因为它挡住所有人（与记忆注入「出错整轮不带」的取舍相反，这里错误代价不对称）。

## 5. 数据模型（迁移分支 acme_0004，全局表、不进 RLS，显式带 workspace_id 过滤——对齐记忆三表的做法）

| 表 | 关键列 | 说明 |
|---|---|---|
| `quota_workspace_setting` | workspace_id (PK), monthly_total_tokens, mode ('block'\|'warn'), updated_by, updated_at | 空间月总额；没行 = 不限 |
| `quota_member_setting` | workspace_id + user_id (PK), monthly_tokens, mode, updated_by, updated_at | 个人额度 |
| `quota_group_setting` | workspace_id + group_type ('department'\|'user_group') + group_id (PK), monthly_tokens, mode, updated_by, updated_at | 部门/用户组默认 |
| `quota_grant` | id, workspace_id, user_id, month (YYYY-MM), extra_tokens, reason, granted_by, granted_at, PK(id) | 临时加额；查询只取 `month = 当前月`，月底自然失效 |
| `quota_change_log` | id, workspace_id, target（空间/人/组/加额）, before, after, mode, changed_by, changed_at, PK(id) | 变更记录；只插不改 |

-group_id 引用内核 `department`/`user_group` 的 id，不外键（跨模块松耦合），删除组后遗留规则在解析时按组不存在而忽略，页面标注「组已不存在」。

## 6. 路由（都经扩展的 `setup_api` 挂载，鉴权走内核 access：系统管理员/空间管理员/本人）

管理端（空间管理员）：
- `GET/PUT /api/workspaces/{id}/quota/setting`——空间总额与模式（页面四卡与对话框）
- `GET /api/workspaces/{id}/quota/overview`——成员列表一次拿全：每人 本月已用/有效额度/额度来自/临时加额/状态（ok|接近上限≥85%|已用完），含解析依据（个人/组/默认/不限）
- `GET/PUT/DELETE /api/workspaces/{id}/quota/member/{user_id}`——个人额度
- `GET/PUT/DELETE /api/workspaces/{id}/quota/group/{type}/{group_id}`——组默认
- `POST /api/workspaces/{id}/quota/grants`、`GET .../grants?month=`——临时加额（当月列表）
- `GET /api/workspaces/{id}/quota/changes?cursor=`——变更记录（分页）
- `GET /api/workspaces/{id}/quota/suggestion`——最近 30 天每人用量的平均/中位数/P90/最大者与建议默认值（P90 向上取整到 10 万的整倍数）、折算轮数与费用

系统管理员：`GET/PUT /api/system/workspaces/{id}/quota`——空间月总额（官方入口在「系统 → 空间管理」；第一版入口放在额度页顶部，系统管理员可见可改，空间管理员只读——入口差异在文档里注明，行为一致）。

个人端：
- `GET /api/quota/me?workspace_id=`——本人本月：已用/有效额度/剩余/恢复日期/状态（`settings.usage.top` 与输入框提醒共用）

## 7. 前端（扩展 frontend/src/quota/）

- **「额度」标签页**（`admin.usage.tabs`，排在「统计」后）：四卡 + 参考行（含「填入默认额度」）+ 成员表（搜索、状态筛选、加额/设额度动作）+ 标签内子标签（成员 / 部门与用户组 / 临时加额 / 变更记录）。
- **设额度对话框**：数字输入 + 折算（约 N 轮对话、填了单价的约 N 元）+ 该人/该组最近 30 天中位数与 P90 + 拦截/只提醒单选。
- **部门与用户组标签**：组列表（来自内核 access）+ 每组默认额度；成员归属多处时列表里标注「取最高」。
- **临时加额标签**：当月加额列表（人、数额、原因、操作人）+ 新增对话框。
- **变更记录标签**：时间倒序，谁把谁的额度从多少改到多少。
- **我的用量**（`settings.usage.top`，挂在个人设置「我的用量」顶部）：本月已用/额度/剩余/恢复日期的进度条；≥85% 出「接近上限」，用完出「已用完，X 月 1 日恢复」。
- **输入框提醒**（`chat.composer.top`）：仅提醒模式下超额或接近上限时展示提醒；拦截模式下超额时调 `block(reason)`（输入框不可发、悬停说原因——后端反正会 429，这里只是提前说）。

## 8. 边界与规则细节

- **没有配置 = 全链路不限**，判定直接返回（与官方「不定就是不限」一致；扩展装了但没配任何额度时不多拦人）。
- **空间没设总额、个人没设额度**：只提醒能力也没了基点——页面明确提示「未设置即不限」。
- **成员被移出空间**：member_setting 行保留（再回来还生效），overview 不再列出非成员；组消失同 §5。
- **多角色**：判定与页面都按 access 现有的「系统管理员 / 空间管理员 / 成员」三档走，不另造角色。
- **IM 认出的人**（channel→person 的对话属主是本人）：按本人额度判——官方口径一致。
- **定时任务**（trigger='schedule'）同样判（到点激活也是开始一轮），超了这一轮不开始，任务回错误说明——由内核把 QuotaExceeded 翻译成各端提示。
- **月份边界**：判定与加额都以「判定时刻的部署时区自然月」为准；跨月 0 点前后的边界由查询即时计算，无缓存即无窗口问题。

## 9. 里程碑

**M1——判定与额度标签页（能拦、能看、能设）**
- acme_0004 迁移（五张表）；`quota.set` 判定登记（解析规则 + 聚合 + QuotaExceeded）；额度标签页（四卡 + 成员列表 + 个人额度 + 空间总额）；`settings.usage.top`；输入框拦截。冒烟：设额→超限拦截（429 与文案）→改额度→临时加额→月底失效口径（伪造 occurred_at）→不限与只提醒。

**M2——部门与用户组、参考建议值、变更记录、仅提醒闭环**
- 组默认（取最高）；`suggestion`（P90 建议值 + 折算）与「填入默认额度」；变更记录标签；85% 接近上限与仅提醒模式的前端提醒（`chat.composer.top`）；部门与用户组标签页。冒烟补：多组取最高、组消失忽略、变更记录逐条对上、85% 文案。

**非目标（第一版）**：按模型的差异化额度、按天的额度、配额预警通知（IM/邮件）、系统自调模型的排除开关——记在设计里，等用起来再说。

## 10. 与官方商业版的差异

- 功能面做到官方文章描述的口径（见 §1 逐条对齐）；交互细节（卡片排布、文案）按我们的实现来。
- 官方入口「系统 → 空间管理」里设空间总额，我们第一版放在额度页顶部（系统管理员限定），行为一致。
- 官方未公开实现细节（判定的缓存与并发控制、变更记录的保留时长），按 §3/§5 自行取舍。

# 企业扩展包设计文档（自研）：空间管理 · 企业技能 · 企业 MCP

> 前置阅读：《授权机制与扩展分析.md》。本文是第一期的实现设计——在**不改任何开源文件**的前提下，写一个自己的扩展包，补齐三个缺失的管理功能。
>
| 功能 | 工作量 | 一期 |
|---|---|---|
| ① 空间管理（新建/改名/关闭/列表） | 小 | ✅ |
| ② 企业技能管理（平台层 CRUD + 发放 + 收编） | 中 | ✅ |
| ③ 企业 MCP 管理（平台层 CRUD + 发放 + 收编） | 中 | ✅ |
| 记忆、扩展知识源 | 大 | 二期 |

## 0. 关键事实（决定了设计形态）

1. **三个功能都不需要新建表、迁移、RLS**。服务层和存储全部开源并已在跑：
   - 空间：`access/workspaces.py`（`open_workspace` / `all_workspaces` / `rename_workspace` / `close_workspace`）
   - 技能：`skills/platform.py`（`PlatformSkillAdmin`，`ApiContext.platform_skills` 已装配，`app.py:463`）
   - MCP：`tools/mcp/enterprise.py`（`EnterpriseMcpAdmin`，`ApiContext.enterprise_mcp` 已装配）
   → 扩展对象声明 `model_modules=() , rls_tables=(), migrations=None`，扩展包是**纯胶水**：路由 + 错误映射 + 页面。
2. **权限判定在服务层内部已完成**（`PlatformSkillAdmin._actor`、`_EnterpriseAdmin._require`、`workspaces._require_system_admin` 都要求系统管理员）。路由层只负责：取 `Principal`、调服务、映射错误。双层保留（路由不重复判权，也不省略传参）。
3. **开源代码已经预留了路由路径**：`apidocs/__init__.py:86` 把 `/api/system/workspaces` 分组为「空间管理」——上游预期扩展就把空间管理挂在这个前缀下。本文照此办理。
4. **审计不用注册**：`audit/actions.py` 对未登记路由走 `_derived()` 自动生成动作名（如 `workspace.create`）；企业 MCP「本空间停用/收窄」的路由（`enterprise-mcp/disable` 等）开源已登记。
5. **空间切换已开源**：`GET /api/workspaces`（`access/api.py:107`）+ 用户菜单切换（CHANGELOG:152）。建出第二个空间后，成员侧立刻可用，不用做任何前端改动。
6. **授权校验器是自己的**：直接返回固定 `valid` + 模块名，不做签名体系（校验器保护的是扩展作者，作者是我们自己）。

## 1. 总体架构

### 1.1 包形态

```

│       ├── extension.py             # Extension 对象：装配三个路由组

│       ├── skills_api.py            # ② 企业技能路由
│       ├── mcp_api.py               # ③ 企业 MCP 路由
```

### 1.2 后端入口点（pyproject.toml）

```toml

[project.entry-points."knowwork.extensions"]
enterprise = "acme.kw_enterprise.extension:Enterprise"
```

`license.py`：

```python
from knowwork_server.extensions import LicenseState

class Verifier:
    def verify(self) -> LicenseState:
        return LicenseState(status="valid", message="自研扩展（内部授权）",
                            modules=frozenset({"enterprise"}))
```

`extension.py`（照 `tests/extensions/demo.py` 的骨架，那是官方给出的模板）：

```python
class Enterprise:
    name = "acme-enterprise"
    license_module = "enterprise"       # 与授权 modules 对上
    model_modules: tuple[str, ...] = () # 不建表
    rls_tables: tuple[str, ...] = ()
    migrations = None                   # 无迁移分支

    def setup_api(self, ctx):
        return [*workspaces_router(ctx), *skills_router(ctx), *mcp_router(ctx)]

    def setup_worker(self, ctx): ...   # 一期无后台任务，留空
    async def start(self): ...         # 无内存态
    async def aclose(self): ...
```

- **鉴权**：每个路由用 `Annotated[Principal, Depends(ctx.principal(None))]`（会话身份，不设 API Key 范围）。系统管理员判定在服务层内部，天然把普通成员 403。
- **错误映射**：技能路由 import `knowwork_server.skills.api` 的 `call_service` / `read_archive` / `revision_of`（开源模块，直接复用，避免漂移）；MCP 路由照抄 `tools/mcp/api.py` 的 `_call` 模式（`McpError → HTTPException(status, detail)`）。

## 2. 功能①：空间管理

### 2.1 API 设计（前缀 `/api/system/workspaces`，全部系统管理员）

| 方法 | 路径 | 服务层调用 | 说明 |
|---|---|---|---|
| GET | `/api/system/workspaces` | `access.workspaces.all_workspaces(user)` | 全部未关闭空间：`{id, name, createdAt, owners[]}` |
| POST | `/api/system/workspaces` | `open_workspace(actor, name=, owner_user_id=)` | 新建。请求体 `{name, ownerUserId}` → 201 `{id, name}` |
| PUT | `/api/system/workspaces/{id}` | `rename_workspace(actor, id, name)` | 改名。服务层判「该空间所有者或系统管理员」，路由无需再判 |
| DELETE | `/api/system/workspaces/{id}` | `close_workspace(actor, id)` | 关闭（软删除）。`Conflict` → 409（默认空间不能关） |

错误映射：`AccessDenied → 403`、`Conflict → 409`、`NotFound → 404`（复用 `access/errors.py` 的异常类型）。

### 2.2 页面设计（`/admin/workspaces`）

```
┌──────────────────────────────────────────────────────────┐
│ 空间管理                                    [+ 新建空间]   │
├──────────────────────────────────────────────────────────┤
│ 名称        创建时间      所有者            操作           │
│ 默认空间    2026-01-05   zhang@…           改名           │
│ 销售部      2026-11-04   li@…              改名 · 关闭     │
└──────────────────────────────────────────────────────────┘
  新建对话框：[空间名称] [所有者 ▾(搜成员)] [取消] [创建]
  关闭确认：警告文案「成员将立即失去访问，系统管理员也不再能进入；数据保留，
           重新开放需另行安排」+ 输入空间名确认
```

- 所有者选择器数据源：`GET /api/workspaces/{ws}/users?q=`（`identity/api.py:171`，开源已有）。
- 「默认空间」行不显示关闭按钮（服务层也会拦，界面先行提示「平台配置所在空间」）。
- 改名直接行内编辑（服务层允许空间所有者改自己的空间名）。
- 建完提示「成员邀请在各空间管理后台 → 成员里进行」，链接跳对应空间。

### 2.3 不做的事

- 空间成员/部门管理：每个空间自己的管理后台已有（开源）。
- 空间切换 UI：已开源，建出第二个空间自动出现。
- 空间删除（物理删除）：服务层只有软删除，不提供物理清除。

## 3. 功能②：企业技能管理

### 3.1 数据流（现状，全部开源，只补管理入口）

- **平台层**：技能存在默认空间 `scope_key="platform"` 的行里；`audience` 是发给哪些空间（`["*"]` 或空间 id 列表，上限 500）。
- **空间层**：`GET /api/workspaces/{ws}/platform-skills`（`layers_api.py`，开源已挂）展示到达本空间的企业技能 + 内置 Word/Excel/PPT；本空间停用/收窄路由（`platform-skills/disable|enable|users`）也已开源并带审计。
- **缺的**：系统管理员对平台层本身的 CRUD 视图 = 插槽 `admin.skills.enterprise` 的 PanelItem。

### 3.2 API 设计（前缀 `/api/platform-skills`，平台级、不带 workspace_id）

| 方法 | 路径 | `PlatformSkillAdmin` 调用 | 备注 |
|---|---|---|---|
| GET | `` | `skills(user)` | 列表，`SkillView.to_json()` |
| POST | `` | `install(user, archive)` | multipart ZIP；`read_archive(request, limits.max_archive_bytes)`；201 |
| GET | `/{skill_id}` | `get(user, skill_id)` | 详情 + `releases[]` 版本历史 |
| PUT | `/{skill_id}/draft` | `replace_draft(user, id, archive, expected_revision=)` | `If-Match` 头带草稿修订号（`revision_of`） |
| POST | `/{skill_id}/publish` | `publish(user, id, expected_revision=)` | 201，`ReleaseView` |
| POST | `/{skill_id}/enable` / `/{skill_id}/disable` | `set_enabled(user, id, bool)` | |
| PUT | `/{skill_id}/env` | `set_env(user, id, changes)` | 只回 `envFilled` 名单，不回值；审计记名字不记值（照 `skills/api.py:190` 的 `annotate`） |
| PUT | `/{skill_id}/audience` | `set_audience(user, id, workspaces)` | `{workspaces: ["*"]}` 或 id 列表；未知空间 422 |
| DELETE | `/{skill_id}` | `delete(user, id)` | 204 |
| GET | `/promotable` | `promotable(user)` | 全空间已发布空间技能清单（空间、名字、版本） |
| POST | `/promote` | `promote(user, workspace_id, skill_id)` | 收编；`already_promoted` → 409 前端提示「已是这一版」 |

### 3.3 页面设计（「技能 → 企业」页签的系统管理员视图）

```
┌────────────────────────────────────────────────────────────┐
│ [上传技能 ZIP]  [从空间技能收编…]                            │
├────────────────────────────────────────────────────────────┤
│ 名称      版本     状态     发给哪些空间        操作          │
│ 合同审查  v3      已发布   全部空间            详情 · 停用    │
│ 报表生成  v1      草稿     未发放              详情 · 发布    │
└────────────────────────────────────────────────────────────┘
  详情抽屉（复用开源 SkillDetail）：版本历史、环境变量、草稿替换
  发放编辑器（AudiencePicker）：◉ 全部空间  ◯ 自选 [空间多选框，数据源功能①的列表]
  收编对话框：空间 ▾ → 技能 ▾（promotable 数据源）→ [收编]
```

- 组件复用：`SkillDetail / ZipPicker / EnvDialog / ReviewDialogs`（`web/src/features/admin/skills/`，经 `@knowwork/web` import）。
- 与空间页签的边界：系统管理员的面板里**包含**本空间设置区（插槽语义如此，见 `UpperSkills.tsx` 注释「管理企业技能本身，连同本空间的设置」）；非系统管理员不受影响。
- 收编后的语义照服务层：第一次生成新企业技能；同一空间技能再收 = 新草稿；同名冲突 409。

## 4. 功能③：企业 MCP 管理

### 4.1 数据流（现状，全部开源，只补管理入口）

- **平台层**：服务存在默认空间 `scope="enterprise"`，名字 `ent_<名字>`；`audience` 同技能；到达空间默认全体成员可用。
- **空间层**：`GET /api/workspaces/{ws}/enterprise-mcp`（`build_enterprise_here_router`，开源已挂）——空间管理员停用/收窄，审计已登记；成员连接、OAuth 回调（`/api/mcp/oauth/callback`）也都开源。
- **缺的**：系统管理员对平台层的服务登记/发放 = 插槽 `admin.tools.enterprise` 的 PanelItem。

### 4.2 API 设计（前缀 `/api/enterprise-mcp`）

| 方法 | 路径 | `EnterpriseMcpAdmin` 调用 | 备注 |
|---|---|---|---|
| GET | `` | `list_servers(actor)` | `McpServerView.of(record, redirect_uri, {})`（企业服务无 promotedTo） |
| POST | `/probe` | `probe(actor, url)` | 登记前探测：OAuth / 凭据 / 自动注册 / redirect_uri |
| POST | `` | `create(actor, body)` | `McpServerCreate`（校验在服务层；连不上不保存） |
| GET | `/{server_id}` | `get(actor, id)` | |
| PATCH | `/{server_id}` | `update(actor, id, body)` | 名称、地址、请求头、超时、启停 |
| DELETE | `/{server_id}` | `delete(actor, id)` | 204；各空间收窄授权残留无害（服务层注释已说明） |
| POST | `/{server_id}/sync` | `sync(actor, id)` | 重拉工具清单 |
| PATCH | `/{server_id}/tools/{tool_name}` | `configure_tool(actor, id, tool, body)` | 单工具三档（允许/需确认/禁用）与分组 |
| PUT | `/{server_id}/audience` | `set_audience(actor, id, workspaces)` | 同技能的 audience 规则 |
| GET | `/promotable` | `promotable(actor)` | 全空间（空间，服务）清单 |
| POST | `/promote` | `promote(actor, workspace_id, server_id, body)` | body 为系统管理员重填的凭据（`McpServerCreate`）；工具三档按原名带过来 |

路径参数校验照开源模式：`IdPath`（`^[A-Za-z0-9_.\-]{1,64}$`）、`ToolPath`。

```
┌────────────────────────────────────────────────────────────┐
│ [接入 MCP 服务]  [从空间服务收编…]                           │
├────────────────────────────────────────────────────────────┤
│ 名称         地址              认证     可用工具  发给哪些  操作 │
│ ent-工单    https://…        OAuth    12      全部空间   详情 · 同步 │
│ ent-CRM     https://…        API Key  5       自选(2)   详情 · 删除 │
└────────────────────────────────────────────────────────────┘
  登记对话框（复用 ServerDialog/AuthFields）：URL → probe 结果驱动
```

- `redirect_uri` 取自 `EnterpriseMcpAdmin.redirect_uri` 属性，部署地址变化时自动跟随。

## 8. 风险与注意事项

- **不改开源文件**：三个功能靠现有服务层 + 现有插槽都能完成。若后续想要更精细的审计动词或 apidocs 分组，优先提上游 PR 而不是本地改（保证升级无痛）。
- **权限唯一真闸在服务层**：路由绝不自己实现"是否系统管理员"逻辑，避免两处判定漂移；但也不省略 `principal` 注入（审计与 API Key 范围都靠它）。
- **audience 校验排除已关闭空间**：`set_audience` 内部用 `all_workspaces`（只回未关闭的），发放目标永远有效；空间关闭后到达它的服务自然失效。
- **默认空间 = 平台配置空间**（`PLATFORM_WORKSPACE_ID = "default"`）：企业技能、企业 MCP、模型配置都存它名下；UI 上永不提供关闭入口。
- **收编并发**：两人同时收编同一技能靠 `lock_scope` 行锁 + `already_promoted` 判定，前端按 409 提示刷新即可。
- **OAuth 回调地址**：企业 MCP 的 redirect_uri 依赖部署对外地址，跨网段部署（内网登记、外网使用）要先确认回调可达。
- **命名空间隔离**：`license_module` 用自有名（`enterprise`），包名带 `acme` 前缀，避免未来装官方扩展时入口点同名冲突（`verify_license` 对多校验器直接判 invalid，宁缺毋滥）。
- **一期不做**：记忆（要设计存储与提取策略）、扩展知识源（要实现知识源协议）——把 `setup_worker`、`ProvidedTools`、`ProvidedSources`、`turn_context` 的接缝留在骨架里，二期填充。

## 9. 上游升级与长期维护

### 9.1 原则：麻烦程度取决于一条纪律

**我们的功能一行都不碰上游文件。** 做到了，升级就只是"拉代码 + 跑测试 + 换镜像"；做不到，每改一个上游文件，那个文件的合并成本每升一次涨一次。本文档的功能设计已按零改动完成（审计用自动生成动词、apidocs 分组上游已预留 `/api/system/workspaces`）。

### 9.2 仓库分层

```
上游 KnowWork (github.com/knowflow-ai/KnowWork)     ← 只读，跟着升级
        │ git fetch（或直接换镜像版本）
        ▼
我们的部署仓库（fork 或纯 compose 覆盖）             ← 只有构建胶水
        │ 构建时注入
        ├── backend wheel（acme-knowwork-enterprise）← 独立 repo，独立版本
        └── frontend KNOWWORK_WEB_EXTENSIONS 入口    ← 独立 repo
```

**拉取方式二选一**：

- **方案 A（推荐）：零 fork**——上游代码原样 clone 只用于构建（或 Dockerfile `FROM` 官方镜像叠装 wheel）；升级 = 改基础镜像版本号重新 build，git 操作为零。
- **方案 B：fork 只加构建胶水**——

  ```bash
  git remote add upstream https://github.com/knowflow-ai/KnowWork.git
  git fetch upstream --tags
  git merge upstream/main        # 没改过上游文件 → 永远 fast-forward，零冲突
  git merge v0.0.5               # 或直接跟 tag
  ```

上游自己的升级路径本就是镜像式的（`guide/deploy.md:77-85`）：checkout 新 tag 拿编排文件、`deploy/.env` 的 `KNOWWORK_VERSION` 换版本、迁移在 api 启动时自动执行。

### 9.3 升级时的四个耦合点

| 耦合点 | 稳定性 | 破坏时的表现 |
|---|---|---|
| `extensions/contract.py` 的 ApiContext | 上游注释承诺"按需加字段"（加法演进） | 极少破坏 |
| 我们 import 的内部模块（`skills.api.call_service` 等） | **无承诺**，可能重构 | Python import 时直接报错，藏不住 |
| `web/src/slots/registry.ts` 插槽类型 | TS 类型化 | 前端编译期报错，藏不住 |
| deploy compose 结构 | 随版本可能变 | 构建期发现 |

### 9.4 升级流水线（照抄上游对 DSH 的三条纪律，README.md:141）

1. **锁版本**：扩展包的测试环境钉住上游版本（如 `knowwork-server==0.0.4`）；
2. **升级前跑准入测试**：CI 流水线「拉上游新源码 + 装扩展 wheel + 全套 pytest + 前端 build + E2E 冒烟」→ 绿了才发我们的新镜像；
3. **跟 CHANGELOG**：重点筛提到 `extensions/contract`、`slots`、`ApiContext` 字段变化的条目。

### 9.5 成本预期

- 正常一次升级：改版本号 → CI 跑完 → 换镜像，**半天以内**，大概率零代码改动；
- 0.x 阶段内部接口会有小漂移（CHANGELOG 可见 DSH 依赖在 0.2.1-rc.2 → 0.2.2-alpha.2 之间动过），预算每次升级 **0.5~2 天**修适配，均为编译期/测试期可定位的小修；
- 升级的麻烦不是"合并代码"，而是"重跑测试"——这正是扩展架构的意义：上游免费维护平台的其余部分。

## 10. 开发环境与工作流

### 10.1 目录布局

```
/home/lqsj/projects/
├── KnowWork/                    ← 上游 clone，MinerU 等在制特性在这做（功能分支）
├── KnowWork-stable/             ← worktree，钉在 v0.0.6，扩展联调用
└── acme-kw-enterprise/          ← 扩展包独立 git 仓库（backend/ + frontend/）
```

扩展包**不在 KnowWork 仓库里**——零改动原则决定了它是独立的包，对 KnowWork 仓库零提交，所以不需要 branch 也不需要 worktree 来"放它"。

### 10.2 为什么用 worktree 而不是切 branch

在制特性（MinerU）的改动未提交时，切分支要么被迫 stash（半成品悬着），要么把半成品带进联调环境（扩展要按干净的 v0.0.6 测试）。worktree 让两个工作区物理隔离：

```bash
git worktree add ../KnowWork-stable v0.0.6
```

- 共享同一份 `.git` 对象库，不占双份磁盘；
- 各自独立的 `.dev/`（嵌入式 PostgreSQL、密钥、日志），联调环境天然全新，删掉即重置；
- `main` 永远快进跟上游 tag；MinerU 收进 `feature/parser-tier`；扩展包版本独立。

### 10.3 起步命令（对照 guide/development.md）

```bash
# worktree 里拉起干净的上游全套（一次性）
cd ../KnowWork-stable
cd runtime-host && npm install && cd ..
cd web && npm install && cd ..
docker build -f deploy/docker/sandbox.Dockerfile -t knowwork-sandbox:dev .
cd server && uv sync

# 后端：装进 worktree 的 venv，入口点即注册（不写进 pyproject/lockfile）
uv pip install -e ../../acme-kw-enterprise/backend

# 前端：worktree 的 web/.env.local（新文件，不修改上游跟踪文件）
echo 'KNOWWORK_WEB_EXTENSIONS=../../acme-kw-enterprise/frontend/src/install.ts' > ../web/.env.local

# 拉起整套；系统信息页应显示扩展已启用
uv run python ../scripts/dev_stack.py
```

注意：
- **端口冲突**：dev_stack 固定端口（7300/8000/8001/5173），两套栈别同时跑；
- **依赖注入方式**：始终用 `uv pip install -e`，不用 `uv add`——只动 venv 不动 pyproject/lockfile，扩展"在不在"全凭装没装，与授权机制同构。

# KnowWork 授权机制与扩展分析

> 基于 v0.0.4 源码分析（2026-11-04）。系统设置页显示「没有安装授权，只启用开源功能」时的完整行为、原理与自行扩展的可行性。

## 1. 授权起作用的原理和路径

全部代码在 `server/src/knowwork_server/extensions/` 三个文件里。

### 三层设计

1. **授权只是一个"状态"，不是运行时开关**
   - `LicenseState`（`license.py:14`）：`status`（none / valid / expired / invalid）+ `modules`（授权包含的模块名集合）
   - 唯一判定函数 `allows(module)` = status 是 valid 且模块名在集合里
   - **开源代码不做任何签名校验**——校验逻辑在闭源扩展包自带的 LicenseVerifier 里（`license.py:3`："真正的保护在扩展包自己，扩展的代码不开源"）

2. **发现靠 Python 入口点（entry points），两个组**（`contract.py:32-33`）
   - `knowwork.license` → 注册授权校验器（扩展包装进镜像后自带）
   - `knowwork.extensions` → 注册扩展对象，每个扩展声明 `license_module`（它需要授权里的哪个模块）

3. **门禁在启动加载那一刻，一次判定**
   - `loader.py:107`：`active = [e for e in installed if license_state.allows(e.license_module)]`
   - 判定之后运行期**没有任何 license 检查点**

### 启动时序

```
进程启动（3 处入口都调 installed_extensions()，@functools.cache 进程内只发现一次）
├─ api:     app.py:465
├─ worker:  ops/worker.py:114
└─ 迁移:    db/migrate.py:68
        │
        ▼
verify_license()  loader.py:63-79
├─ knowwork.license 组为空 → NO_LICENSE（系统信息页那句话 = license.py:25 的 message）
├─ 注册了多个校验器 → invalid（"无法确定以哪个为准"）
├─ load() / verify() 抛异常 → invalid（"按没有授权处理"）
└─ 正常 → 校验器自己读授权文件、验签名，返回 LicenseState
        │
        ▼
discover()  loader.py:97-111
├─ 遍历 knowwork.extensions 入口，逐个 load + 校验必备属性（失败只跳过该扩展）
├─ allows(license_module) 分成 active / skipped（skipped 带原因，写日志）
└─ 产出 Extensions { license, installed, active, skipped }
        │
        ▼
装配（按进程角色）
├─ api  _setup_extensions  app.py:493：逐个调 setup_api(ctx) 拿路由 → 挂 /api（app.py:561）
│        可选 setup_internal → 挂内部端口（app.py:586，只给宿主/扩展自己的服务回调）
│        装配报错 → 整个扩展去掉（两种路由都不挂，不留半截）
├─ worker  ops/worker.py:121：调 setup_worker(ctx) 注册后台任务
└─ start()  app.py:208：权限规则加载完、开始服务之前调；报错整个服务拒绝启动
        │
        ▼
系统信息页展示  system/info.py:44-48：license.message + 每个扩展的启用/跳过原因
```

### 两个刻意的设计点

- **迁移不看授权**（`migrate.py:66-68`）：迁移分支取自 `installed` 而不是 `active`——只要装了扩展包，表就必须建齐。授权过期时数据还在，续上授权重启即恢复。
- **授权变更要重启才生效**：`installed_extensions()` 有 `functools.cache`（`loader.py:114`），换授权文件 = 重启 api 和 worker。

一句话：**授权不是"检查每个请求"的守卫，而是"启动时决定加载哪些闭源模块"的过滤器**；开源功能完全不经过这条链路。

## 2. 无授权时缺的功能与使用限制

### 缺的功能（扩展包提供的）

| 功能 | 细节 | 无授权时的实际状态 |
|---|---|---|
| **新建空间（多空间）** | 底层服务在开源（`access/workspaces.py:71` 的 `open_workspace`），但管理接口和页面在扩展里 | 只有初始化建的一个「默认空间」，**单空间使用** |
| **企业技能管理** | 系统管理员上传、发布、启停、删，选发给哪些空间，从空间技能「收为企业技能」 | 只能用内置 Word/Excel/PPT 技能 + 各空间自己传的空间技能 |
| **企业 MCP 管理** | 系统管理员登记一次 MCP 服务、发给全部/选定空间 | 各空间管理员自己接自己的 MCP |
| **记忆** | 记忆写入工具、每轮给模型补的上下文、回合结束后排后台提取（`contract.py:54-62`） | 完全没有 |
| **扩展知识源** | 额外的知识源类型；多跳检索、视觉检索、`knowledge_fetch` 取原图/原文件要求知识源支持 | 内置 KnowFlow 连接器不支持 trace、fetch、视觉检索 |
| **扩展工具 / 后台任务 / UI 插槽** | `system.nav`、`insights.base.action` 等插槽 | 都为空 |

### 使用限制

- **没有人数/席位、调用次数、有效期限制**——开源代码里不存在这类逻辑
- 开源功能全量可用：组织部门树授权、知识库检索与引用、空间技能、空间级 MCP、渠道、OIDC 登录、问答大盘、运行记录、审计、沙箱、内置 Word/Excel/PPT 技能
- 实际约束就是**单默认空间**

**结论**：开源版 = 完整的单空间平台；授权解锁的是"平台级"能力（多空间、企业技能/MCP 统一下发、记忆、扩展知识源）。

## 3. 多空间有什么用

- **按部门/团队各开各的空间**：每个空间一套独立的成员、知识库、技能、MCP、渠道、审计和问答大盘，PostgreSQL 行级安全按空间隔离（README.md:226）
- **一个人进多个空间**：能进两个以上空间时用户菜单直接切换（CHANGELOG:152-154）；邀请可以指定落进哪个空间
- **系统管理员跨空间**：能进任何空间；配合企业技能/企业 MCP，一次上传、选空间下发

**判断**：单团队用开源版完全够——部门树授权在单空间里已覆盖"谁能用哪个知识库/技能"。多空间的价值在**组织隔离**和**平台运营**（一个平台服务多个团队）。

## 4. 关于 DeepSeek Harness 的记忆

- DSH = DeepSeek Harness（Agent 内核，MIT，npm `@deepseek-ai/dsh`，当前锁 0.2.2-alpha.2）
- **DSH 本体没有内置记忆**；社区插件生态里有很多记忆插件（dsh-memory、dsh-agent-memory、dsh-auto-memory 等），但基本是会话级/本机 markdown 的，没有企业级的归属和权限概念
- KnowWork 没走"装 DSH 记忆插件"这条路，原因：
  1. 记忆需要按用户、按空间存取、判权、进审计、后台提取——这些数据全在业务服务（PostgreSQL + RLS），原则是"DSH 里不放密钥、不做权限判断"（README.md:123）
  2. 管道已铺好在开源侧：宿主端 `runtime-host/plugins/dsh-host/src/turn-context.mjs`，业务端 `conversations/turn_context.py`、`tools/provided.py`——缺的是记忆的**提供者**（扩展包），不是宿主能力
  3. 保持"只用 DSH 官方扩展点、不 fork、跟着 DSH 升级"（README.md:69）

## 5. 闭源模块不在本仓库

- 全仓库没有任何 `[project.entry-points]` 声明 → `discover()` 永远发现 0 个扩展，`verify_license()` 永远返回 `NO_LICENSE`
- 没有 `.whl`、没有私有包引用；`NOTICE` 只列第三方 MIT 依赖（DSH、WeKnora）
- 搜出来的 `enterprise*` 文件全是**开源代码**

### 值得注意：很大一部分"被授权的功能"其实是开源的

| 层 | 开源情况 |
|---|---|
| 企业技能服务层 `skills/platform.py` | ✅ 开源 |
| 企业 MCP 服务层 `tools/mcp/enterprise.py` | ✅ 开源 |
| 建表迁移 `0037_enterprise_mcp.py` 等 | ✅ 开源 |
| 记忆管道（宿主 `turn-context.mjs`、业务端 `turn_context.py`、`provided.py`） | ✅ 开源 |
| 装配点 `app.py:463` 把 `platform_skills`、`enterprise_mcp` 无条件塞进 `ApiContext` | ✅ 开源 |
| **LicenseVerifier + 各扩展的 `setup_api`/`setup_worker`（路由、页面、记忆提供者）** | ❌ 闭源包 |

## 6. 可以自己写扩展包替代

### 法律层面：Apache 2.0 允许

- 允许商用、修改、**闭源衍生**；单独写的扩展包 `import knowwork_server` 不触发 copyleft 义务
- 义务：不改开源代码本身的话，基本只剩保留 LICENSE/NOTICE 声明
- 红线：不能拿 KnowWork 商标宣传成"官方版"（Apache 2.0 第 6 条不授商标权）；自用无所谓
- 官方闭源包不在 repo 里，不存在反编译问题，也不需要

### 技术层面：两端插槽机制都是公开的

**后端**（`server/tests/extensions/demo.py` 是完整可跑的模板）：

1. `pyproject.toml` 注册入口组 `knowwork.license`（校验器）+ `knowwork.extensions`（扩展对象）
2. 实现 Extension 协议：`name / license_module / model_modules / rls_tables / migrations / setup_api / setup_worker / start / aclose`
3. 校验器最简单：自己是作者，直接返回 `LicenseState(status="valid", modules={"my_module"})`，不需要真的做签名体系
4. `pip install` 进 server 环境（或打进镜像）→ 重启 → 生效

**前端**（`web/src/slots/registry.ts`）：

- 开源构建时 `@knowwork/extensions` 指向空的 `none.ts`，所有插槽为空
- 构建带扩展的镜像时设环境变量 `KNOWWORK_WEB_EXTENSIONS` 指向扩展包入口文件，导出 `install(register)`
- 插槽名是公开的类型化接口：`admin.skills.enterprise`、`admin.tools.enterprise`、`system.nav`、`insights.base.action` 等
- 扩展前端可用核心组件与 API 封装（别名 `@knowwork/web`）

### 工作量分层

| 功能 | 工作量 | 原因 |
|---|---|---|
| 新建空间管理 | **小** | `open_workspace()` 服务层开源现成，只缺路由 + 页面 + `system.nav` 插槽 |
| 企业技能管理 | 中 | `SkillService` platform 范围整个开源（`ApiContext.platform_skills` 已装配），写管理路由 + 页面接上去 |
| 企业 MCP 管理 | 中 | 同上，`EnterpriseMcpAdmin` 全开源（`ApiContext.enterprise_mcp`） |
| 记忆 | **真功夫** | 管道开源（turn_context / provided / on_turn_ended 三件套），但存储表、提取策略、检索、按人判权的产品设计要自己做 |
| 扩展知识源 | **真功夫** | 要实现知识源协议（trace / fetch / 视觉检索），对接外部系统 |

## 总结

这套架构对二次开发是**故意敞开的**：扩展合同、服务层、插槽、测试模板、wiring 测试全部开源。官方闭源包的本质是"官方写好的管理界面 + 记忆 + 连接器"，不是技术壁垒。单空间自用的话，新建空间、企业技能管理几天就能自己补齐；记忆和扩展知识源才是真正的开发项目。
